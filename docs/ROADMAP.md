# RepoCity Roadmap — the path to 10/10

This roadmap turns RepoCity from a strong prototype into a release that holds up as a portfolio centerpiece and a Show HN launch. It is ordered by impact: what a first-time visitor sees, then what they feel, then what a reviewer finds when they read the code. Findings come from a full code audit plus live testing across eight repositories of different sizes and languages (13 files → 17,013 files), including error paths.

**Current state, honestly:** small repositories (< ~50 files) render as genuinely beautiful neon cities — the window shaders, color crowns, and glow are portfolio-grade. Data accuracy is excellent: byte percentages cross-check against GitHub linguist within ~3%, canonical resolution and commit pinning work, and determinism holds across reloads. But mid-size cities settle into a frame where the city occupies under 20% of the screen, large repositories render as near-black silhouettes, one of the app's own preset chips fails, and the tallest building is a lockfile in four of eight tested repos. (An earlier draft also reported a 30-second build freeze; that was an artifact of a GPU-less test browser and is corrected in item 6.)

> **Progress, 2026-08-03.** Phase 1 is done and a visual-quality pass is under way in stages — see [Visual quality pass](#visual-quality-pass-in-progress) at the foot of this document for what has landed, what is measured, and what is next.

## Phase 1 — The picture (ship-blockers)

The product is a picture. These five items decide whether anyone shares it.

**1. Fix resting camera framing.**
After the intro settles, a 236-file repo (pallets/flask) occupies ~15% of the viewport, bottom-center, with the stats panel floating over empty space. Cause: the framing fits the full bounding volume, and a single tall outlier (usually a lockfile tower) forces the camera far back. Fit to a high-percentile bounding box instead of the max, raise minimum screen coverage of the city to ~60–70% of the free viewport (excluding panels), and verify against small/mid/large fixtures. Replace the pinned tuning-constant tests in `camera.test.ts` with coverage-ratio assertions so the suite tests the *behavior*, not the numbers.

**2. Make large cities readable.**
microsoft/vscode and mrdoob/three.js render as black slabs on a black ground: emissive windows shrink below one pixel at overview distance and nothing else carries light. Add selective bloom (or distance-scaled emissive boost), lift the ground plane out of pure black, and give buildings a minimum silhouette luminance at distance. Acceptance: a vscode-size city at resting camera reads as a lit skyline in a thumbnail.

**3. Dethrone the lockfiles.**
Tallest building in testing: `test.mp4` (react), `pnpm-lock.yaml` (vue), `uv.lock` (flask), `o200k_base.tiktoken` (vscode). Height is file-size rank, so generated/binary bulk always wins the skyline — the most prominent thing in the city is the least interesting file in the repo. Rank height within *source* files; render lockfiles, media, and generated blobs as distinct low structures (warehouses, tanks, billboards — the metaphor is free). The "TALLEST" stat should name a file a developer cares about.

**4. Make the sample represent the repo.**
three.js: 453 of 1,720 rendered files come from `examples/`, while `src/` — the actual library — gets 32 buildings. vscode renders 798 of 17,013 files (4.7%) with no visible disclosure of the drop from 5,000 selected → 798 rendered. Byte-weighted sampling structurally favors asset directories. Blend count-proportional and byte-proportional allocation per district, guarantee source-directory floors, and state plainly in the UI: "rendered 798 of 17,013 files." Also close the test gap: the largest-remainder allocation path in `worker/sampling.ts` is currently never executed by any test.

**5. ~~Never ship a failing preset.~~ Reopened once, now closed.** This was ticked off when the `torvalds/linux` chip was removed, but `rust-lang/rust` was left in the header with exactly the same failure: "GitHub returned more data than RepoCity can process safely." A first-time visitor clicking a chip in the app's own header got an error. All seven chips were then loaded one by one; only that one fails, and it is gone. Two others appeared to fail during the check and did not — the verification itself had tripped the Worker's 3-requests-per-60s actor limit, which is worth remembering before reading any batch result as a product defect.

  Repositories at that scale remain unsupported, and that is now the honest position rather than a hidden failure: making them work needs a different payload strategy — a paginated fallback traversal already exists — or a pre-baked snapshot. The error UX the original item asked for is in place; the full reason appears in the visible status and the typed input survives a failure.

## Phase 2 — The feel

**6. ~~Kill the build freeze.~~ Corrected — measured, and it is not real.** The original finding ("mid-size builds lock the main thread for 30+ seconds; screenshots time out") came from an automated browser without GPU acceleration and did not reproduce on real hardware. Measured with `PerformanceObserver` longtask entries in Chrome against microsoft/vscode (17,013 files → ~740 rendered): **325 ms** of total main-thread blocking on a desktop GPU, and **1.16 s** at 6× CPU throttling, in one or two tasks. A CPU-side profile of the generation pipeline puts `buildLayout` + `buildCity` + rooftops + streets + traffic at **~65 ms** for 4,725 files, so there is no geometry hot spot to chunk. Moving generation into a Web Worker would add a Three.js buffer-transfer boundary and real complexity to save ~300 ms; it is not worth it. The one real defect was that the synchronous block swallowed its own "building city · N files" status update — fixed by yielding for a paint before construction starts. Revisit only if profiling on low-end hardware shows blocking above ~2 s.

**7. Verify and polish controls.** Synthetic drag registered as click-select and scroll didn't zoom during automated testing — verify orbit/zoom by hand on trackpad, mouse, and touch; if intentional inertia/thresholds are eating small deltas, tune them. Add touch support and an on-canvas zoom affordance; the current hint bar ("drag orbit · scroll zoom · click inspect") is easy to miss.

**8. First-run experience.** A fresh visitor gets an unannounced auto-build of react/react with a long quiet fly-in. Make the intro deliberate: brief hold on the finished skyline, then a short camera move — and show a one-line "what am I looking at" caption. The City Index legend is excellent; surface a compact version of it on first load.

**9. Legend and language hygiene.** The three.js legend reads "Other 59%" at the top and also has a lowercase "other 7%" aggregate — two rows, same word, different meanings. Split assets into real categories (Models, Textures, Audio…), merge or rename the tail bucket, and fix the `detectLanguage` branch where `.npmrc`/`.bashrc`-style rc-files all return `json` (the `properties` branch is unreachable for them).

**10. ~~Poster and share surface.~~ Done, and the real problem turned out to be different.** Both halves of this item were already fixed: the og:image landed in `adc0f22`, and the poster font bug in `3ef89c9` — where `document.fonts.ready` proved insufficient on its own, because it settles pending loads but never *requests* a face the page has not used, and nothing on screen uses the italic-500 Fraunces the caption draws with.

What was actually wrong is that every public image — the og:image, the README hero, the three gallery shots — was generated by hand and then never regenerated, so all of them advertised a city with floating building tops, no interior streets and none of the district architecture. Hand-made assets drift silently. `npm run capture:media` regenerates all five from pinned repositories at the sizes `index.html` and the README already reference, so refreshing them after visual work is one command.

## Phase 3 — The code (reviewer-proof)

**11. Break up `main.ts`.** 1,263 lines, 49 functions, 42 mutable module-level bindings, zero tests, ~23% of the frontend. Extract: scene bootstrap, repo-load orchestration, picking/selection, explorer UI, breadcrumbs/stats, poster capture. Target: no file over ~400 lines, and the extracted modules become testable (they currently can't even be imported under vitest because of module-scope DOM lookups).

**12. Deduplicate the copy-paste debt.** Partly done: the window-grid shader constants now live once in `facade-shader.ts` and both surfaces include them; language detection lost one of its three copies when `detectLanguage` moved into `file-class.ts` so the treemap could classify; and `hashString` is exported from `core/random.ts` and used for district typologies. **Still open:** the remaining unreachable language-detection copy; `streetLength` three times; `streetKey` twice with *different* float semantics; ~80 lines of validators duplicated across the worker/frontend trust boundary; and `signHash` (`city.ts`) plus `hashColor` (`palette.ts`) still sitting beside `core/random.ts`. One shared module each.

**13. ~~Add the missing quality gates.~~ Mostly done.** ESLint and Prettier are in the repo, `npm run lint` gates `npm run check`, CI runs the whole gate, and `noUnusedLocals`/`noUnusedParameters` are on — which did flag the dead exports this item named (`getPalette`, `BRAND`, `void announce;`), all now gone. **Still open:** coverage thresholds for `src/core`, `src/data` and `worker`. Note that `npm run capture` and `npm run measure` are deliberately outside the gate: they need a GPU and network access.

**14. Worker efficiency and headers.** Every request — including 100% cache hits — burns two GitHub calls before the cache lookup, capping an unauthenticated deployment at ~30 builds/hour and a token at ~2,500 req/hour. Add a short-TTL ref→SHA cache and negative caching for 404s. Honor `If-None-Match` (an ETag is emitted but 304s are never returned). Stop forwarding the server token's `X-RateLimit-*` quota headers to anonymous clients. Add the CSP and security headers that `SECURITY.md` already promises, then make `SECURITY.md`'s release checklist true.

## Phase 4 — The launch

**15. ~~README with proof.~~ Done.** The README leads with a 7-second recording of the entrance — `mrdoob/three.js` loading, the skyline assembling, the camera sweeping onto the resting shot — produced by `npm run capture:gif` so it can be re-recorded whenever the renderer changes. Badges and the gallery are in place. The still hero was dropped: a second picture of the same city directly under the animation was redundant weight.

Two things the recording exposed. `rust-lang/rust`, the repository originally wanted for it, does not load at all — see item 5. And the capture tooling's "is it still building?" test matched `/building/i`, which also matches the *success* message "5,000 buildings from a deterministic sample", so every capture in the project had been sitting out the full 180-second build timeout before continuing on a secondary check. Loading flask went from 261 seconds to 3 once that was corrected. The GIF recorder had copied that wait inline rather than sharing it, which is how the bug survived being fixed once; the wait now lives in one place.

**16. Deploy to repo.city.** Workers Paid plan, `GITHUB_TOKEN` secret, WAF rules per the threat model, custom domain, and the og:image endpoint. The share URL (`#repo=…&commit=…&seed=…`) is already deterministic — every shared link reproduces the exact city, which is the viral loop.

**17. Launch assets.** Show HN post that leads with the picture and the determinism story ("same commit + seed = same city, forever"); a gallery thread; CONTRIBUTING.md and issue templates so the first wave of visitors can land as contributors.

### Verified strengths to protect while doing all this

Determinism across reloads (byte-identical layouts, tested); data accuracy (linguist-consistent byte percentages, canonical repo + commit pinning, complete-tree proofs); the small-repo aesthetic — window shaders, crown lighting, palette; the security posture of the worker (validated hostile input on both sides of the trust boundary, no client-side tokens, pseudonymized rate-limit keys); and the City Index legend, which honestly explains what is and isn't data. These are the product's soul — every change above should ship with a screenshot diff against a fixed (repo, commit, seed) to prove the soul is intact.

## Visual quality pass (in progress)

A staged pass driven by eight defects found in live testing. Each stage is verified with `npm run capture` against a fixed set of repositories, not against fixtures — a synthetic uniform grid gave the wrong answer twice. From Stage 3 on, `npm run measure` adds numbers to the pictures: it reads a dev-only probe out of the running app and reports what the shader is actually being fed, per building, at the solved camera.

### Landed

**Stage 1 — vehicles, signs, framing, horizon** (`1410f4a`, `2b64cee`)

- Every vehicle rendered black. `vertexColors: true` was set on geometry with no `color` attribute; three defines `USE_COLOR` from the material without checking the geometry, `MeshBasicMaterial` has no `defaultAttributeValues` fallback, so the unbound attribute read `(0,0,0,1)` and zeroed `vColor` before `instanceColor` applied. Six materials had it. Ground traffic was black too — on near-black asphalt, so it read as working. The old test asserted the CPU-side colour buffer, which was correct throughout; the new one asserts the material/geometry pairing.
- District signs were yaw-only billboards, invisible edge-on from above. They now copy the camera's orientation.
- The framing solver sized on a box capped at 2.4× the real skyline, so it fitted mostly empty air. Now 1.35. Measured cost: the worst-azimuth aim sits ~0.5 skyline-heights below ground, versus +0.33 before.
- The bare plain around every city was a ground disc with `fog: false` that scene fog could not touch. Fogging it was necessary but not sufficient — the sky dome reached its bright horizon colour exactly at eye level, so the seam merely moved. One `NIGHT_COLOR` now feeds the clear colour, the fog and the dome's lower band.

**Entrance and idle** (`bf41568`)

- The drift resumed 8s after interaction and took 4s to reach speed — a ~12s wait. Both halved.
- The entrance is now four beats over 6.6s: a three-quarter sweep, a dip, an aerial reveal at 2.6× the hero elevation, then a descent onto the hero pose. Elevation multipliers are relative to the hero's ~18°, so they read far lower than they look; anything under ~0.8 collapses the city to a band on the horizon. Distance multipliers below 1.0 are clamped to `safeRadius` and silently flatten the move.

**Stage 2 — layout and size distribution** (`d4d3786`)

- **The layout was deleting most of the repository.** The gutter between cells was an absolute world-unit subtraction that compounded per depth level (0.35 at the root, 4.75 by depth four), and `squarify` dropped any cell whose padded rect hit zero. react rendered 1,181 of 5,000 selected files while the UI reported all 5,000 as selected. The gutter is now capped per axis at a fraction of that axis. A regression test builds a five-level tree; against the old code 43 of its 44 files disappear.
- Footprint was an isotropic shrink triggered by an anisotropic test, so a 40×10 parcel produced a 12×3 building marooned in its own plot. Buildings now fill their plot on both axes.
- Plot area was exactly proportional to bytes; it is now compressed by a 0.55 power. Ordering is intact, extremes are pulled in. The weight is carried beside the node — `node.size` is the real byte count and both the explorer and the height ranking read it.
- Heights came from two disjoint ranges (6..30, then 48..72) with nothing between, and `coreRatio` stepped at the 0.4 percentile in a way that made the visible mass *drop* 23% as rank rose. Both are continuous now.
- `block` — 40% of source buildings — had no detail geometry at all.

**Stage 3 — brightness consistency**

Measured first, with a new `npm run measure`: a dev-only probe (`src/city/brightness-probe.ts`) recomputes on the CPU exactly what the fragment shader derives per building, importing the same constants the GLSL is generated from so the two cannot drift. Run against flask, react and vscode at the resting camera. The measurement moved two of the four suspects and found a fifth.

- **`aLit` was the real headline, as suspected.** Measured at 2.59× on 10.1–11.1% of buildings in every repository — react's 3,482 JavaScript buildings spread 3.0×, essentially all of it this one binary flag. Forcing every window on already multiplies the grid's mean energy by `1 / WINDOW_LIT_MEAN` = 1.79× for free; the shader then applied a further 1.45× on top. The look worth keeping is a fully lit tower, not a second material, so the extra factor now pulls the other way and the subset lands at 1.5×. The 0.7-vs-1.3 rim step (1.86×), which stacked on the same flag, is re-centred to match while holding its old population mean.
- **`aSpan` → `rcAssist` is no longer a source of variance — it is saturated.** The roadmap guessed Stage 2 had removed the variance; what Stage 2 actually did was remove the *dynamic range*. Fixing the layout gutter sextupled the building count in the same land area (vscode 798 → 4,854), so every footprint shrank and mid/large cities now sit pinned at the top of the ramp: median `rcAssist` **1.000** for both react and vscode, against the 0.1 and 0.85 the file's own prose claimed. Within a city it is now uniform (1.19× and 1.14× spread), so it is not a brightness-consistency problem. It is a different problem, recorded below.
- **`floorShift` is dead where it mattered.** It is scaled by `1 - assist`, and assist is 1.0, so measured per-building floor spread is exactly 1.00× in react and vscode. It survives only in small repositories (flask python 1.28×). Now that luminance is normalised downstream it is a pure hue shift, which is what it was always described as.
- **`languageEmissiveBoost` confirmed, and worse than a misnomer.** Per-language window luminance spread 1.56× (html 0.418, yaml 0.747): magenta is starved of the green that carries 71% of Rec.709 luminance, so the magenta half of the palette read as a dimmer material than the cyan half for identical emissive energy. Every language-coloured surface — windows, rim, the facade floor, crowns, roof strips — now passes through `rcNormalizeLuma`, a clamped hue-preserving scale toward a target luminance. Hue still separates the languages, which is the palette's own stated primary differentiator; value no longer does it by accident.
- **New: the amber anchor was unreachable.** `TINT_OFFSET` was *subtracted* from a language's warmth before the colour ramp read it. Warmth is capped at 1.0 by the palette table, so the reachable ramp position capped at 0.9 — and the amber segment only begins *above* 0.9. JavaScript and Java, the palette's two declared amber hero languages, therefore rendered as pure magenta at every camera where the per-floor jitter is faded out, which since Stage 2 is every mid/large resting camera. react is 49% JavaScript, so the gallery's "JavaScript amber" claim was false for the one repository that most demonstrates it. The offset is now a rescale, so the full warmth range maps onto the full ramp. `brightness-probe.test.ts` locks this: the hero languages must reach the amber anchor with no per-floor help, and the cyan zone must still pin to cool.

`rimPulse` (±12%, animated) was left alone — it is an order of magnitude below the mechanisms above, and being animated it reads as life rather than inconsistency.

**Stage 3b — geometry: connected tops, and a city that reads as one**

Four defects found in live testing: building tops showed inverted layers that intersected each other, upper masses floated clear of the buildings carrying them, some buildings rendered completely flat, and — the one that matters most — cities of different sizes did not look like the same kind of place. All four reproduced, and all four trace to Stage 2 changing two systems without re-deriving what depended on them.

- **Crowns floated clear of their cores.** The core is `totalHeight × coreRatio`; the crowns were placed at hardcoded fractions of `totalHeight` (0.86, 0.89, 0.66, 0.885, 0.98) fitted against the *old stepped* `coreRatio` of 0.76/0.82/0.52. Stage 2 made that a continuous taper down to 0.55 and left the fractions alone, so **every `tower` in every city rendered its top floating — measured at 16.2 world units of empty air**, and `setback` was 2.8. Refitting the numbers would have rotted again at the next change, so the numbers are gone: `planCap()` is a pure function that tiles from the core's *actual* top to the declared height, each piece reaching down into the one below. The rendered top now equals `totalHeight` by construction. That also fixed `rooftops.ts`'s floating pylons and the camera reserving up to 15% of its vertical framing for empty air, both of which already measured to `totalHeight` and were wrong only because nothing reached it.
- **"Inverted layers"** was the same root cause seen from the side: the parapet is emitted at the core top, and the crown started *below* it, so a wide brim jutted out of a narrow tower's waist. Pieces are now width-monotonic above the brim. Light strips were also being passed a crown's vertical *centre* for three profiles and a roof plane for the other two — one argument meaning two things — so roof outlines sat partway down a tower's flank.
- **Spires were base-origin** (`geometry.translate(0, 0.5, 0)`) while being placed with a centre `y`, overshooting the declared height by 12%; and their width floor was absolute, so on a narrow building the spire came out **8× wider than the tower carrying it**.
- **"Semi-identical … a dead compound."** Measured: `squarify` drives plots toward aspect ratio 1 (p50 1.29) and Stage 2 made buildings fill both axes, so every building was a near-square box — and **one silhouette accounted for 19.9% of the city, with four shapes across 5,000 buildings.** Shape now comes from the file's parent directory (`typology.ts`), so a folder's files are built alike and the folder next door is built differently. That is simultaneously the variety and the organisation the city lacked, and it stays honest — shape encodes *where in the repository you are*. Most common silhouette **19.9% → 2.8%**; plan aspect p95 **1.97 → 3.03**. The height curve went 2.0 → 3.0 so the top few percent read as landmarks instead of a flat top edge; still strictly increasing, so "height is size rank" is untouched.
- **"Slop."** Plot area was wildly uneven because `weigh()` applied the area exponent at *every* level including directories, and `x^0.55` is sub-additive — so a folder always got less area than its contents claimed, compounding per level. **Two identical 3 KB files six levels apart differed in plot area by 2,484×, while the entire byte range spans about 175×: tree depth outweighed file size by an order of magnitude.** Compression is now applied once, at the leaves, with directory weight the sum of its children. Ratio **2,484× → 1×**, plot-area spread **1144× → 34×**. The gutter also now decays with depth instead of charging an arterial's width between two sibling files (coverage 47% → 55%), and non-source bulk is compressed harder and capped at 15% of the map, which is what removed the flat lockfile plateau covering a third of react.

**Two changes were built, measured, and reverted** — recorded because the reasoning is not obvious. Removing the land cap makes building proportions *perfectly* size-invariant (median 1.7:1 from 13 files to 5,000, against 2.8→17.8 before), and it looks worse: a large city covers four times the ground with no extra height, the camera pulls back to fit it, and the skyline flattens into a distant pancake of cubes. Scaling heights with the city instead simply moved the drift. Density is what makes the picture read as a city, so the cap stays at 240 and the residual drift is accepted and documented. What remains is a *framing* problem — a large city should be entered, not fitted on screen — which belongs with the camera work below.

Coverage where there was none: `architecture-details.ts` had no test file at all, which is why this shipped. It now has a vertical-continuity contract; `geometry-probe.ts` and `testing/repo-tree.ts` run `buildLayout` and `buildCity` against each other at realistic scale, which nothing did before — `city.test.ts` fed hand-built rects that never came from the layout, and that seam is exactly where these defects lived.

**Stage 3c — every facade lit the same way**

Found in live testing: a subset of buildings had every window lit, which flattened them into a single block of colour beside neighbours made of dots.

- **The `aLit` flag is gone.** It forced roughly one building in ten to have *every* window on. It was meant as variety, and it isn't: a fully lit facade has no dark cells left to break it up, so the building flattens into a solid slab of one colour beside neighbours made of dots. Every building now rolls the same per-cell hash, and the only difference between two facades is which cells it happened to light. The rim's paired 0.72/1.08 brightnesses collapse to the single population mean, so overall city brightness is unchanged.
- **Removing the flag was not enough: the largest buildings stayed solid, from a defect introduced by the typology work above.** Rendering the window mask, `sideMask` and `rcAssist` as RGB showed the offenders at **`assist` ≈ 1**, i.e. the shader believed the largest buildings on screen were a few pixels wide, and at full assist the grid resolves to its average, which *is* a flat colour. Cause: `aSpan` was `min(width, depth)`, and the new slab typology deliberately narrows one axis to 0.52 — so the widest, most visible walls in the city reported themselves as half as wide as they are and dropped into the distant-rescue path up close. `planSpan()` now uses the geometric mean, the side of the square with the same footprint, so one narrow axis can no longer drag the ramp to zero. `min` was harmless only while every building was nearly square.
- **Window emissive 2.0 → 1.4.** Read against the bloom pass's 0.72 threshold: at 2.0 a lit cell reached 1.2, and on a large near facade the blooming cells merged until the grid disappeared. This was already true of the cyan half of the palette and became true of the rest when Stage 3's luminance normalisation lifted the dimmer languages to the same target. The crown's own multiplier is now derived from this one rather than being a second literal, which is exactly how the two grids drifted apart before.

**Tooling.** `npm run capture` and `npm run measure` drove the app by typing into the header and waiting for the status pill, which raced the auto-build; a run reported flask and react as the same 3,883-building city. Both now navigate by the app's own share hash and refuse to sample until the sidebar names the repository they asked for. It caught a real mislabel within a minute of landing. It also surfaced that **`facebook/react` now redirects to `react/react`** — the app resolves canonical names correctly, so the check allows an owner change and logs it.

**Stage 3d — the city gets streets**

Streets were derived *after* the fact: the renderer merged district bounding boxes into bands, took whatever gaps were left over, and clipped those against every plot. The treemap tiles its rect edge to edge, so there was nothing left over. Measured on generated cities — **one interior street at 13, 120 and 1,000 files, three at 5,000**, against a four-segment perimeter ring, with interior roads covering 0.28–2% of the ground. The ring was the network, which is why traffic drove around the city rather than through it.

Inverted: a directory now takes a road margin out of its rect *before* its children are allocated, and `buildLayout` returns those strips alongside the cells. The road is empty by construction, so nothing has to be clipped to discover whether it survived, and `planStreets` — pure, no DOM, finally testable — joins the abutting rings of neighbouring directories into single through-routes. Because the margin is a fraction of the rect being subdivided, and that rect shrinks with nesting, the hierarchy falls out for free: arterials around top-level districts, alleys around leaf folders. Interior streets go **1–3 → 14–75**, roads take about a quarter of the ground, and files inside a folder now pack as a block instead of each getting its own moat.

Two things this cost, both caught by the geometry probe rather than by eye. The ring is charged at every ancestor, so a flat fraction compounded exactly as the old per-cell gutter did — land coverage fell to 27% and the hard-won depth-independence of plot area went back to 2.5×; decaying the fraction per level fixed both. And `padding`/`depthScale` in `LayoutOptions` no longer configured anything, so they are removed rather than left as settings that silently do nothing.

**Stage 3e — reviewing a large repository against a small one**

Two reactions to `facebook/react` beside a 86-file repository: some buildings looked insanely tall, and some colours looked wrong. Both were real, and one was self-inflicted.

- **The colours were a regression from the `TINT_OFFSET` fix.** Making amber reachable for the hero languages also made the amber knee at 0.9 *crossable* by the per-floor hue jitter. Measured on react: **700 of 4,889 buildings — 14% — showed magenta floors and amber floors on the same wall**, because `markdown` sits at 0.72 on the ramp and the jitter reaches 0.94; `rust` and `html` cross it too. Amber is supposed to mean "JavaScript or Java". The jitter is now scaled to the room left inside a language's own zone, so it varies shade and never identity, and it stays smooth rather than piling floors up on the boundary. JavaScript and TypeScript were always immune, being pinned at the ends of the ramp — which is exactly why a TypeScript-dominated repository looked clean and react did not.
- **The heights were a knock-on from `HEIGHT_CURVE` 3.0.** That curve dropped the median to 14 units while leaving the tallest at 72, so tallest-to-median ran 4.9×. At 2.3 the median returns to 19 and the ratio to 3.6×. The trade is real and measured: a gentler curve on unchanged plots makes the median building *slimmer*, 7.5:1 to 10.2:1. Rendered against react before accepting — the skyline is visibly more even and the density hides the extra slimness, so the number regressed while the picture improved. Both halves are asserted now, the slenderness bound and the tallest-to-median ratio, so neither can be undone by accident.

- **A third finding, and the clearest rule violation of the three: walls were being painted.** `facadeGlow` washed the entire side surface in the language colour — `sideMask` is 1 across every wall face — at 5% rising to 19% toward the top. The premise of the whole facade is that a building is black and its colour comes from its windows, and this contradicted that outright. It was gated on `rcAssist`, intended to mean "too small on screen to show windows", but that gate turned out to be near-binary in practice: measured median assist is **0.000 for a 226-file repository and 0.997 for react**. So a small city never triggered it and a large one triggered it everywhere. The wash is now roofs-only. A roof genuinely has no windows to carry it, and without a floor a wide depot cap reads as a hole punched in a distant city, which is what the term was added for in the first place.

  Removing it does not restore window detail to a large city, and it is worth being clear about why: at that same saturated assist the window grid also resolves to its *average*, so a six-pixel-wide building is a flat colour before any wash is added. That is information density, not shading, and it is the same saturated ramp recorded below.

Worth recording plainly, because it is the honest answer to "why does a big repository look busier": at a fixed land cap, more files means smaller plots, so buildings must get either thinner or shorter. There is no third option without more ground, and more ground was built, measured and rejected for making the city read as a distant pancake. A 5,000-file repository looking different from an 86-file one is partly inherent.

The `safeRadius` floor this item blamed does not bind. Solved distance against a real city box is about 300 while `safeRadius` is about 206, so it is the height/width *fit* that decides and lowering the floor would change nothing. A first attempt to prove otherwise appeared to confirm the old story only because the test fixture omitted `totalHeight` and produced a degenerate box — worth remembering that this module returns plausible-looking numbers for a malformed box rather than throwing.

What the investigation did find was a defect in the capture tooling, not the app. `hideInterface` hid the panels with `display: none` and dispatched a synthetic resize; the app drops that because the window itself has not changed size, so the framing stayed solved for a viewport that still had panels in it. Every capture and every generated media asset was composed for one viewport and rendered in another, leaving the city inset where the sidebar had been. With the refresh wired up, hiding the panels now moves the camera in from 252 to 221 and the city overflows both axes. Real users were never affected by that one: a genuine panel toggle already refreshed.

The exported poster had the same shape of defect and *is* user-facing. `capturePoster` switched the camera to 16:9 and re-rendered without re-solving, so the poster inherited a pose composed for the band between the panels and came out with the city inset and the sidebar's space empty beside it. It now recomposes for the full bleed — but only while `composedPose` is true, meaning the camera is still where the rig put it. Once the user has orbited to a view of their own the poster stays exactly what they are looking at, because recomposing that would quietly move their shot.
